## Experiment ID

## Objective

Capture a first, time-based sequential read measurement with FIO on Windows, using a fixed file, block size, and queue depth, so later experiments have a documented baseline job rather than an undocumented ad-hoc run.

This experiment is **not** a device characterization study and is **not** a claim about peak SSD performance.

## Limitations and interpretation

- **Single job, single run.** There is one job (`error` 0) and no repeats, so there is no estimate of run-to-run variance beyond the in-run bandwidth/IOPS samples (`n = 20`).
- **Queue depth 1, sequential read, 128k, ~10 s.** This is a narrow host-level FIO workload. It does not represent maximum SSD throughput, maximum IOPS, worst-case latency, or a vendor spec point.
- **Host-level only.** Results are FIO’s view of reads to `C:\fio-lab\exp001_testfile.bin` via `windowsaio` with `direct=1`. The JSON does not identify the physical device, filesystem, volume, cache, or NAND. These numbers are **not** NAND-level behavior (no FTL, GC, or NAND telemetry).
- **Device unknown.** Project records do not name the SSD (or HDD, RAM disk, or network path) behind that file. Do not attribute the result to a product.
- **File size vs bytes read.** `size` is `256M` while `read.io_bytes` is `6322651136` because `time_based` is `1`: FIO reused the file for the 10-second window.
- **Windows thread fallback.** Process-shared mutexes were unavailable; FIO forced threads. Comparability with Linux `libaio`/`io_uring` jobs is not established.
- **No disk utilization block.** FIO did not record `disk_util` in this JSON.
- **Do not over-read latency.** Report `clat` percentiles and `lat`/`clat` maxima as FIO stored them. Do not treat them as device service time.
- **Not a model input until provenance is complete.** Use as a documented FIO snapshot only; do not claim generalization.
